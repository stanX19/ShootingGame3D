# Procedural Asteroid Assets and WSL Rendering

Status: **Implemented.** This document describes the current asteroid asset pipeline, runtime rendering contract, and WSL launch behavior.

## Purpose

The project uses deterministic low-poly asteroid models and procedural rocky textures generated by a standalone developer tool. Generation stays outside the game runtime, while the game continues to use the existing config-driven model loading path.

On WSL, `make run` selects Mesa's D3D12 driver when it is available and no explicit `GALLIUM_DRIVER` was supplied.

## Ownership and Runtime Boundaries

- Generator source lives under `scripts/gen_model/`, and `make gen_model` is the explicit build-and-run entry point.
- Generated runtime assets live under `assets/Models/asteroid/` and generator build outputs remain under `objs/`.
- `srcs/entities/asteroid.cpp` keeps the config-driven load path and delegates model loading to `ModelManager`. It does not traverse materials or mutate texture state.
- `ModelManager` owns first-load diffuse/normal texture preparation. ECS, collision, spawning, and ring behavior are independent of the visual generator.
- The shared shaded renderer receives only a normal-map availability flag; it contains no asteroid-specific rendering branch.
- Generation is not part of game startup, normal compilation, or frame processing.
- The downloaded asteroid GLB files remain untouched.

## Generated Assets

The generator writes the compatibility asset and two named visual profiles:

- `assets/Models/asteroid/generated_asteroid.obj`
- `assets/Models/asteroid/generated_asteroid.mtl`
- `assets/Models/asteroid/generated_asteroid.png`
- `assets/Models/asteroid/generated_asteroid_normal.png`
- `assets/Models/asteroid/asteroid_small.obj/.mtl/.png/_normal.png`
- `assets/Models/asteroid/asteroid_big.obj/.mtl/.png/_normal.png`

The shared generator keeps actual vertex radii within `0.8–1.0`, uses `2048x1024` maps by default, and emits seam-safe spherical sampling with shared smooth normals. `asteroid_small` uses the approved 12x18 / 396-triangle profile. `asteroid_big` uses the approved 16x24 / 720-triangle profile and separate macro, medium, and fine crater bands. Broad and medium bands feed both the macro geometry and lower-frequency normal-map height field so important basins, rims, ravines, and rock-scale relief survive texture mip reduction; only fine grain, pores, and tiny cracks are allowed to fade at distance. Big texture identity is procedural rather than monochrome: low-frequency material patches, crater-floor darkening, warm rims, cool ravines, and stone-cluster color variation share the same feature masks as the relief. The sunlight shader uses the sampled albedo directly rather than blending it halfway with white. The albedo and normal textures use deterministic broad noise, ridged rock detail, fine grain, and seeded crater bowls/rims with identical first/last longitude columns. `ModelManager` generates diffuse/normal mipmaps once on first file-model load and applies trilinear filtering.

The generated files are runtime source assets and are kept with the project so a fresh checkout does not require the generator before launching the game. Generator build outputs remain under `objs/`.

## Generator Structure and Design

- The generator is split into six files: `asteroid_generator.hpp/.cpp` for shared algorithms, `asteroid_small.hpp/.cpp` for the small profile, and `asteroid_big.hpp/.cpp` for the big profile.
- Each profile module explicitly defines the settings it owns. Profile policy is not hidden behind aggregate defaults or a shared `Profile` branch.
- Visual model generation is independent from collision-proxy generation; collision preprocessing reads completed model files through its own pipeline.
- Geometry, normal maps, and albedo use shared feature masks. The intended hierarchy is micro, medium, and macro feature spacing of `1:10:100`; only microdetail is expected to disappear through mipmapping.
- Normal-map strength is profile-specific. Material identity is not compensated for by silently changing global shader lighting.

The six-file split is an ownership boundary, not just a naming convention: shared topology, noise, feature-mask, texture, and normal-map algorithms stay in `asteroid_generator.*`; each profile explicitly defines its complete settings in its own pair. This prevents a later profile change from silently changing the other asteroid.

The big profile uses three identity bands with spatial spacing `micro:medium:macro = 1:10:100`. Macro and medium bands must be present in geometry, the lower-frequency normal field, and the albedo masks. Micro stones, pores, and grain are intentionally allowed to fade through mipmapping. Normal-map strength is profile-specific because one global slope multiplier cannot make both small stones and large terrain landmarks readable.

Material identity belongs in the generated albedo and its shared feature masks: crater floors, rims, ravines, and stone clusters need distinct color regions, not only lighting relief. The shaded material samples that albedo directly; gameplay visibility adjustments belong to the entity/render-body brightness, not to an unrelated global shader-lighting increase.

## Performance Evidence

- Generator wall time is not render performance. Repeated-asteroid decisions use a fixed 100-instance scene benchmark separate from asset generation.
- Uncapped WSL/D3D12 measurements record frame latency and synchronized render latency separately. `glFinish()` measures GPU-plus-driver time, not a pure GPU timer-query interval.
- Triangle-count choices use both performance measurements and visual silhouette/feature review. A benchmark winner is evidence, not a profile default by itself.

The current benchmark reports 396 triangles for repeated small asteroids and 720 for the big profile's 100-instance stress scene. These measurements are interpreted together with the matching close-up silhouette and landmark review when profile defaults are evaluated.

The benchmark harness is scratch-only. Generation timing, frame latency, and synchronized render latency are separate measurements; a `glFinish()` result represents GPU-plus-driver time and must not be reported as a pure GPU timer query.

## Runtime configuration

The canonical setting remains:

```json
"units": {
    "asteroid": {
    "modelPath": "assets/Models/asteroid/asteroid_big.obj"
    }
}
```

The existing asteroid entity and model manager continue to use this path. OBJ material and texture references are relative to the model directory.

All runtime models follow the nominal unit-radius convention documented in [model-asset-conventions.md](../model-asset-conventions.md). The asteroid's `0.8–1.0` local geometry range stays inside the nominal broad-phase sphere; runtime loading applies no asset-specific corrective transform. `RenderBody.scale` and `CollisionBody.radius` both continue to use the nominal asteroid `rad`.

## WSL Launch Behavior

When `make run` is evaluated, the launch behavior is:

1. If `GALLIUM_DRIVER` was supplied by the environment or command line, preserve it.
2. Otherwise, if `/dev/dxg` and Mesa's `d3d12_dri.so` exist, launch with `GALLIUM_DRIVER=d3d12`.
3. Otherwise, launch without a driver override.

The override applies only to the game process. Compilation, tests, generator execution, and Git are unaffected.

## Testing and Verification

The pure generator is covered by deterministic Catch2 unit tests without a window, GPU, audio device, input, network, or runtime asset pack. Tests verify topology, exact `0.8–1.0` radius bounds, deterministic output, texture dimensions/variation, cratered normal variation, seam equality, and invalid-setting rejection. Runtime GPU texture preparation is verified by build/source review and bounded manual launch, not headless unit tests.

The shared sunlight shader samples the normal map only when the current material has `MATERIAL_MAP_NORMAL`; other shaded models keep the geometric-normal path. The tangent frame is derived from screen-space position/UV derivatives, so the OBJ does not need tangent attributes.

Manual verification loads the generated OBJ through the existing game path and confirms the asteroid remains near-spherical, irregular, textured, and visibly responds to fine surface noise through lighting.

## Non-Goals

The following concerns are intentionally outside this asset and launch contract: frustum/distance culling, LOD, batching/instancing, particle profiling, collision broadphase, ECS layout, entity pooling, ring population, roughness maps, displacement mapping, compiler optimization flags, and additional generator frameworks.

## Design Lessons

- Visual quality and collision fidelity are separate asset concerns. The visual generator produces the render model; collision preprocessing consumes completed model files and applies its own simplification and topology rules.
- A nominal radius is an asset invariant, not a value to “fix” later in the renderer or entity factory. The generated asteroid geometry stays within `0.8–1.0`, while runtime scale and collision broad-phase policy remain explicit elsewhere.
- Profile ownership matters. Keeping every profile's settings in its own module prevents a change to the big asteroid from silently changing the small asteroid.
- Feature masks are the shared source of truth for geometry relief, normal-map relief, and material identity. This keeps macro landmarks visible across representations while allowing microdetail to fade through mipmapping.
- Asset-generation time and rendering time answer different performance questions. Generation is measured as a tool workload; repeated-asteroid rendering is measured in a fixed scene; synchronized GPU timing is not reported as a pure GPU timer query.
- Checked-in generated runtime assets make a fresh checkout runnable without requiring the generator first. The generator remains an explicit maintenance tool rather than a hidden build or startup dependency.
